# 输入法自动补全字符导致后续输入中断（豆包 iOS）

## 现象（2026-09-19 用户报告）

iPhone + 豆包输入法，在 AgentPort mobile 终端里输入 `(` `)` 或引号之后，
继续输入其他文本时终端不再出现任何字符。

## 本机实测：机制已复现（适配层级）

真实 `@xterm/xterm` 5.5 + `installIosImeRouting`（iOS 归属适配层），
用合成 DOM 事件序列逐事件记录分支判定（复跑命令见
`/tmp/agentport-ime-probe/RESULTS.md`，探针源码
`/tmp/agentport-ime-probe/iosIme.probe*.test.ts`）：

| 变体 | DOM 序列 | 修复前 sent |
|---|---|---|
| V1 | 一次 `insertText` 报告 `(`，DOM 却变成 `()`、光标停在中间，之后照常打字 | `[]`（一个字都不发） |
| V2 | `(` 正常发出，随后补出的 `)` 把光标留在它前面，之后打字 | `["("]`，之后全空 |
| V3 | 输入法把光标跳过自己补出的 `)`，再打字 | `["(", "x"]`（自己恢复，但补出的 `)` 从未发出） |
| V6 | 弯引号 `“”` 光标在中间，之后打字 | `[]` |
| V9 | 无配对（对照） | `["(", ")", "x"]` |

第一处分歧：`reconcile()` 只接受**光标在 textarea 末尾**（`atEnd`）的编辑。
输入法把光标留在自己补出的字符前面时，`atEnd` 永远不会再成立，此后每次编辑
都判为 `unproven-edit` → 不发字节；而 `input` 监听仍在捕获阶段
`stopImmediatePropagation`，xterm 自己的兜底也拿不到事件 ⇒ 终端对之后的
输入完全无反应。次要缺陷：该状态下按退格，DOM 删除被判 `hardware-owned`
丢弃，但按键仍走 xterm 发出一个 DEL —— 抹掉一个终端其实没收到过的字符。

## 真机实测（字节探针，两轮）

在用户 Mac 上建了一个只记录字节的探针会话（raw 模式读 PTY，逐块记录到达 Host
的字节 + 1 Hz 心跳 + 时间戳，`/tmp/ime-probe/capture.py`）。

**第一轮**（中文全角）：Host 一次性收到 6 字节 `（）`（U+FF08 U+FF09），两个字符
都被发送；探针随即因作者自己的 bug 崩溃（`bytes.endswith("\r")` 给 bytes 传了
`str`），之后用户输入的 `555vv（）` 直接落到 zsh 并被 `.zsh_history` 记录 —— 所以
这一轮只能证明"全角 `(` 会把补出的 `）` 一起发出"，没有卡死证据。

**第二轮**（用户按探针屏幕上的 A–D 步骤操作，逐块记录）：

| t | 到达 Host 的字节 | 含义 |
|---|---|---|
| 164.6s | `A` | 控制组开始 |
| 171.4s | `abc` | 控制组文本，正常 |
| 180.3s | `\r` | 控制组回车，正常 |
| 188.2s | `（）` | 只按了 `(`，**输入法补出的 `）` 也一起到达** |
| 201.2s | `\r` | 之间敲的 `abc` **一个字节都没到**；回车照常到达 |
| 206.0s | `“”` | 只按了 `"`，补出的 `”` 也一起到达 |
| 211.0s | `\r` | 之间敲的 `def` 同样没有到达 |
| 230.6s→244.5s | `“”` `\r` `（）` `\r` | 用户重复测试，现象完全一致 |

结论：**配对字符本身被完整发送，之后所有文本编辑都被吞掉，而按键（回车/退格）
仍然有效**。这与本机复现的第一处分歧一致：`（）` 在被插入的那一刻光标还在末尾，
于是走了旧的 `atEnd` 追加分支整段发出；随后输入法把光标移进括号内部且**不产生任何
DOM 事件**，此后每次插入都发生在"已发送文本"前面 → 旧代码判 `unproven-edit` 并静默
（捕获阶段又阻断了 xterm 兜底）。按键不受影响，因为 Enter/Backspace 走 xterm 的按键路径。

## 修复后真机复测（第三轮，中文全角模式）

装上新包后同一步骤重跑（探针记录 `/tmp/ime-probe/fix-verify2.jsonl`），
输入法保持中文全角——打 `(` 会补成 `（）`：

| t | 到达 Host 的字节 | 含义 |
|---|---|---|
| 98.2s | `（）` | 只打 `(`，配对整段发出（与旧版一致，收尾符先到） |
| 100.1s | `\x7f` | 随后回车：按键离开适配层前先把补出的 `）` 从终端撤回 |
| 100.1s | `\r` | 回车照常通过 |
| 106.1s | `（）` | 再打 `(`，配对整段发出 |
| 110.5s | `\x7fabc` | **用户开始打字：先撤回补出的 `）`，再发 `abc`（一次写）** |
| 113.5s | `\r` | 回车 |
| 116.3s | `“”` | 打 `"`，配对整段发出 |
| 132.0s | `\x7fdef` | 同样先撤回再发 `def` |
| 138.2s | `（` | 这次收尾符只作为 ghost 插入（**从未发送**），终端只收到开括号 |
| 143.0s | `ghi` | 用户敲的字母照常到达 |
| 148.0s | `\x03` | 用户结束探针 |

结论：

- **旧版卡死的形状（全角配对 + 光标停在括号内）现在完全正常**：配对之后敲的字母
  一条不落到达，且补出的收尾符被撤回，终端里只剩用户真正敲的字符。
- 两种设备形状都覆盖到了：收尾符"整段发出→被证明不是用户敲的→撤回"（106/116s）
  与收尾符"作为 ghost 从未发出"（138s）。
- 半角一轮（`/tmp/ime-probe/fix-verify.jsonl`）同样通过：`()`、`""` 之后字母到达；
  Enter 前若光标停在补出字符前面，会先发出 `\x7f`（148s 那类单发 DEL 即此路径）。

## 修复边界

`src/terminal/iosIme.ts` 把"输入法插入、用户没敲过的文本"当成一等状态：

- `ghosts`：一次插入中光标没越过的部分（插入时输入法就留在光标后面）登记为
  ghost —— 永不发送、永不计入 DEL（按 Unicode scalar 计数，只统计已发送字符）。
- `lastPadding`：对于"整段插入恰好是一个开闭配对（或单独一个收尾符）"的按键，
  记录它尾部的收尾符区间。当且仅当用户的下一次输入**正好**落在它前面时，说明
  它不是用户敲的：先发一个 DEL 把它从终端撤回，再发用户敲的文本，并把它登记为
  ghost。配对里开括号是用户敲的那一半，永远不会被撤回。
- 按键（回车/退格等）离开适配层之前同样先做这个撤回，所以 `(` 之后直接回车时
  终端收到的是 `（` + 回车，而不是多一个 `）`。
- 只有**编辑区域之后没有已发送字符**时才映射这次编辑（终端是追加式的）；
  无法映射的编辑仍然放弃归属，但不再因此停止映射后续编辑。
- 配对插入即使没有 `beforeinput`，只要 `(base, value)` 的切分唯一也可接受；
  切分有歧义时拒绝猜测。
- 退格：只有在已拥有区域内、且删除目标全是可安全回退的 scalar 时才由 DOM 接管；
  删除 ghost 不发 DEL。

不做的事：不按时间/整句去重，不重写 textarea 内容，不改组合输入与粘贴路径，
不为复杂字形推断删除次数。

## 未验证与残留风险

- 字节探针只能证明"到达 Host 的字节"，**不能逐事件证明手机端 DOM 形状**：例如
  138s 那次收尾符从未发出，究竟是"第二次编辑把光标留在收尾符前"还是"组合输入的
  提交"，字节层看不出来。要定论仍需 Web Inspector 或诊断包 trace。
- **收尾符在终端里可能短暂出现**：配对整段发出后才撤回，因此用户会看到补出的
  字符闪现一下（106/116s 的证据），终态才是"只有用户敲的字符"。
- **没有证据时收尾符留在终端**：如果输入法把光标留在补出字符**后面**（半角一轮就
  是这样），下一次输入是"追加"而不是"落在它前面"，适配层不会撤回它——终端与
  DOM 保持一致，但与"只发用户敲的字符"的严格语义有偏差。
- **用户又敲一次收尾键时输入法会再插一对**（半角一轮 E 步实测）：终端会多出一个
  开括号（与 DOM 一致）。这是输入法本身不为文档场景 overtype 导致的，适配层无法
  从字节层区分"用户想要这个字符"与"输入法又补了一对"。
- 在**已发送文本中间**插入（用户点回行中间再打字）仍然会被拒绝：终端是追加式的，
  适配层不为它改写已显示内容。此时需要把光标移回末尾。
- ghost / padding 区间只在适配层内存里跟踪，textarea 内容不再被重写。
